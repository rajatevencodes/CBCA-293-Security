# Chapter 5. Conclusion

## 5.1 Conclusion

This project built a privacy-preserving pipeline for credit card fraud analytics. A Python pipeline loads 1,852,394 simulated card transactions, protects the personal data with masking, salted SHA-256 pseudonymization, generalization and suppression, proves k-anonymity with k = 5, flags suspicious transactions with four explainable rules, and writes a validated Tableau workbook that reads only the protected file.

The main findings are:

* **Privacy can be measured, not assumed.** With exact states and narrow age bands, 659 of 999 customers were in groups smaller than 5. After generalizing to 4 regions and 5 age bands, every group had at least 5 customers.
* **Simple rules can work on unseen data.** Learned only from the training file, the combined rules caught 57.1% of the fraud in the later test file with a precision of 34.1% (F1 0.427). The best single rule reached F1 0.179.
* **Accuracy is the wrong measure for rare fraud.** A system that flags nothing scores 99.61% accuracy and catches no fraud.
* **Privacy did not reduce detection.** None of the rules needs names, addresses, exact ages or states, so protecting these fields cost nothing in detection quality.

## 5.2 Limitations

1. **Simulated data.** The dataset was generated by the Sparkov simulator [16], [23]. Real fraud is more varied and changes over time [3], so the measured precision and recall show how the method behaves, not how it would perform at a bank.
2. **Rules, not machine learning.** The four rules are easy to explain, but they can only catch patterns similar to the ones learned. Missed frauds (921 on the test file) that do not combine three warning signs will always be missed. Machine learning models can find more complex patterns [2], [4].
3. **Many false alarms.** About 2 false alarms are raised for every fraud caught (2,368 against 1,224). In a real bank each alert costs investigator time [4].
4. **k-anonymity does not stop attribute disclosure.** k-anonymity only guarantees groups of at least 5 customers. If all customers in a group share the same sensitive value, an attacker still learns it (homogeneity attack), and outside knowledge can also narrow down a person (background knowledge attack) [11]. The project does not check l-diversity.
5. **Quasi-identifiers chosen by hand.** The check uses (age band, gender, region). Other fields left in the file, such as the merchant, the exact transaction time and the amount, could help an attacker who already knows some of a customer's purchases.
6. **Salt kept in code.** The salt is in `src/config.py` so that results repeat. Anyone with the code can rebuild the pseudonyms from card numbers. In a real system it must be kept in a secrets vault and never shared with the data [7].
7. **Tableau Public publishes data publicly.** Workbooks published to a Tableau Public profile are freely accessible to anyone [15]. The workbook must only ever use the protected CSV, and it should be kept local or shared only through a private channel.
8. **Batch processing only.** The pipeline runs on files, not on a live stream of payments, and the rule limits are learned once. A real system would need to update its limits as patterns change [3].
9. **Fixed path in the workbook.** The `.twb` file stores the absolute folder of the CSV. On another computer it must be rebuilt with `--tableau-data-dir`.

## 5.3 Future Scope

1. **Stronger privacy models.** Add an l-diversity check [11] on the fraud label within each group, and try differential privacy [12] for the aggregate KPIs shown on the dashboard.
2. **Machine learning layer.** Train a model, for example a decision tree or random forest, on the protected features, and compare it with the rules. A hybrid of rules and a model is closer to industry systems [4].
3. **Cost-based threshold.** Choose the threshold by the money saved minus the cost of checking alerts, instead of F1 alone [3].
4. **Better secret handling.** Read the salt from an environment variable or a secrets manager instead of from code.
5. **More rules.** Add rules based on transaction frequency, for example many payments by one card within a short time.
6. **Real-time version.** Run the same rules on a stream of transactions with a big data tool such as Apache Spark.
7. **Automatic tests.** Add unit tests for each function (for example `mask_card()`, `pseudonymize()` and `k_anonymity()`).
